# The findings CLI

`inspect-audit-findings` runs the deterministic producers (inspect-evals-lint, inspect-dataset, `.eval` header checks) over named Inspect Evals evals and writes immutable run files (the current view is the newest run per producer), parquet and markdown summaries. Producers run in their own `uvx` environments; override with `INSPECT_AUDIT_LINT_CMD`, `INSPECT_AUDIT_DATASET_CMD`, `INSPECT_AUDIT_HAWK_CMD`. A dataset scan through an eval's task has two steps, so the eval's dependencies and inspect-dataset's never mix. First a dump script loads the task with Inspect's own loader and writes its samples to a temporary file. It runs as `uv run --project <root> --frozen [--extra <eval>] [--group <eval>] python`, with the checkout's locked dependencies plus the eval's own extra and group. The environment is a scratch one, by default `~/.cache/inspect_audit/eval-envs/`, so the checkout's `.venv` is never touched; the only thing the editable install writes into the checkout is the gitignored `src/inspect_evals.egg-info`. The scratch environment is shared by every eval scanned from that checkout and synced without removing packages, so it accumulates each eval's extras; versions still come from the lock. The dump reads no `.env`, so a token for a gated dataset has to be in the environment. HF-mode scans run from the caller's directory, where inspect-dataset reads `.env` as it always has. Then inspect-dataset scans a replay of those samples in its own `uvx` environment, with the checkout's locked `inspect-ai` so the samples are read with the same `Sample` model they were written with. Override the steps with `INSPECT_AUDIT_DATASET_DUMP_CMD` (where `{ie_root}` stands for the checkout path and `{eval_deps}` for the eval's flags) and `INSPECT_AUDIT_DATASET_TASK_CMD` (where `{inspect_ai}` stands for the `--with inspect-ai==<version>` pin), and the scratch environment with `INSPECT_AUDIT_EVAL_ENV`.

```bash
uv run inspect-audit-findings run --root ../inspect_evals --out out/ inspect_evals/stereoset
uv run inspect-audit-findings run --root ../inspect_evals --out out/ --featured --logs hawk:<eval-set-id>
uv run inspect-audit-findings summary out/          # re-render from the current view
uv run inspect-audit-findings hawk-sets inspect_evals/scicode
uv run inspect-audit-findings hawk-pull             # fetch scripts/hawk-artefacts.yaml into artefacts/ (gitignored)
uv run inspect-audit-findings leads --out out/ inspect_evals/stereoset   # LEADS.md for an agent
uv run inspect-audit-findings review suppress --out out/ --rule answer_length --eval inspect_evals/stereoset --reason "struct answers"
uv run inspect-audit-findings review accept --out out/ --eval inspect_evals/stereoset --rule duplicate_questions --title "StereoSet has duplicate contexts"
uv run inspect-audit-findings review link --out out/ ISS-0001 https://github.com/UKGovernmentBEIS/inspect_evals/issues/1
```

`--config PATH` names the per-eval declaration of what to scan and which logs count; the default is the packaged `pilot.yaml`. By default the dataset is scanned through the eval's first task in `eval.yaml` (`inspect-dataset scan inspect_evals/<task>`). That way the scan sees the split, config, revision, field mapping and sample ids the eval uses, and findings name the dataset by the location Inspect records for that task, such as `cais/mmlu`. When that location is a local file, as for datasets inspect_evals downloads to its cache, they use the task spec instead, so the same finding has the same fingerprint on every machine. Each entry can declare a different `task`, or HuggingFace settings (dataset path, config, split, revision and field roles) to scan the HuggingFace dataset directly, with `eval.yaml`'s HuggingFace asset as the default path. It can also declare a `task_args` filter for logs, and whether mock-model runs count (they do not by default). An eval without an entry uses every non-mock log it matches. Every run records what it examined under `inputs`, and each eval's `SUMMARY.md` has an Inputs section listing the dataset scanned, the scorers a task scan assumed (the eval's own scorer names, carried from the dump to the replay task so inspect-dataset's scorer-aware scanners judge applicability by them), the logs used and excluded with reasons, and the revision the header checks compared against.

`--review DIR` names the directory holding `suppressions.yaml` and `issues.yaml`, default the out directory; see [review-files.md](review-files.md). The `review` verbs are the only way those files are written: each resolves the selection against the current view, validates, writes, re-renders, and commits when the directory is inside a git work tree. The author comes from `--author 'Name <email>'`, else from git's `user.name` and `user.email` there; without either the command exits 2. A selection that matches nothing, an unknown record id, or a finding another issue already owns is exit 2 with the reason. Summaries group observations by rule with a count and two examples, and list suppressions and accepted issues. `leads` renders one eval's reviewed findings as hypotheses for an agent; see [leads.md](leads.md).

Limitations today: a task scan covers one task per eval (the first, or the declared one), and it imports the eval's code on the host, as running the eval would; a dataset scan skips when there is no task, asset or declaration; the header checks compare against the checkout's `eval.yaml`.
