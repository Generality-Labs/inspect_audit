01

One investigation, several kinds of work

Inspect Auditor is an Inspect agent that investigates whether a benchmark’s scores mean what people think they mean. It reads code and logs, commissions focused checks, and publishes an evidence-backed report.

The investigator chooses the investigation. The package supplies tools, evidence packaging, job controls and a publication contract. There is no fixed rule that every investigation must audit every sample or run an experiment.

Whole benchmark

investigate

Repo + optional paper, logs and steer → autonomous investigation → versioned HTML report. This is the path the current pilots use.

One item at a time

audit

Inspect task + selected items + optional attempts → one audit session per dataset item → structured verdicts in Inspect logs.

Earlier interface

report

A separate conversational synthesis agent over audit logs. It still exists; the investigator does not automatically call it to write its report.

The model itself is served remotely. “Local investigator” means the Inspect controller runs on your machine. Its bash commands run in Docker. Hawk runs the work it commissions. This arrangement avoids putting a local Docker daemon inside a Hawk investigation container.

Model routing is a separate concern. The current outer sessions use OpenRouter. Hawk and Middleman provide remote execution/access and model-routing infrastructure, but a task’s internally created judge must still receive the correct provider and authentication. A successful candidate call does not prove the judge route works; AgentHarm exposed precisely this gap.

03

Follow one investigation

  1. Seed a workspace. Resolve the repository revision, stage source and supplied material, and write /inputs/seed.json. Local source becomes a snapshot; a remote repository can instead be cloned by the agent. Local logs are hardlinked where possible, with copying as a fallback.
  2. Orient. The agent reads the investigating skill, maps dataset → prompt → tools/environment → submission → scorer → aggregation, and inventories logs before opening selected transcripts.
  3. Investigate leads. It compares claims with implementation, inspects existing attempts, writes analysis scripts and tests alternative explanations. These stages are prompt guidance, not a rigid state machine.
  4. Commission work if useful. Write a Hawk eval-set YAML under /workspace. hawk_submit validates it and records a reservation. jobs watches, waits, inspects and collects it. A small benchmark run can create the first transcripts; an audit job can examine selected items.
  5. Maintain evidence. Append actions and corrections to the journal. Update the findings register as claims become supported, qualified or retracted. Save tables, scripts and evidence locators.
  6. Publish. Draft Quarto using the supplied components, render and inspect figures, then call publish_report. Batch mode ends after publication; explicit interactive mode permits follow-up discussion and another version.
Experiment execution is optional. Without remote configuration, the prompt asks for experiment proposals rather than claims that experiments ran. With Hawk, the agent still decides whether another run is worth the budget.

What a per-item auditor actually audits

An AuditItem identifies a benchmark task and dataset item. Its AttemptRef records point to attempts by different models or epochs. Ten attempts at the same question are evidence for one item audit, not automatically ten separate auditors.

Benchmark item

+

→
Audit session
selected checks, evidence, verdicts

The package resolves the original Inspect task, groups attempts by sample ID and stages item material under /audit. Joins need compatible task/dataset identity; an ID alone is not a guarantee that two revisions contain the same question.

05

Skills are instructions plus a small contract

There are two layers. Investigation skills teach repository review, log analysis, experiment workflow and report writing. Audit-item skills define the specific questions a per-item auditor must answer.

Question familyCurrent audit skills
Is the task answerable and its reference defensible?gold-answer · insufficiently-specified
Does scoring credit the right things?answer-format · red-teaming
Was the intended information boundary respected?ground-truth-access · contamination
What happened during execution?environment-integrity · failure-attribution · approach-census
What did the checklist miss?other-findings

This grouping is explanatory, not another implemented taxonomy. Passing items selects audit checks; omitting it currently selects all. A skill’s Markdown teaches the method, while frontmatter declares allowed grades, required detail fields, exceptions to evidence requirements and certain tool grants. record_verdict validates that contract.

Skills do not enforce exhaustive transcript reading or scientific validity. “Enumerate all submitted answers” remains a model instruction. The report’s findings register is also distinct from per-item verdicts: the investigator synthesizes those observations into benchmark-level claims.

Logs: three different paths

SourceHow the investigator sees itWhat is moved
Supplied local logsInspect log APIs over read-only /inputs/logsHardlinks when possible; copies across filesystems. No automatic upload to Hawk.
Supplied remote logslogs(): inventories and sample tables, then selected transcriptsThe outer agent need not download the whole corpus.
Jobs it launchesjobs(): status, sample lists, transcripts and collectionCollection downloads .eval files into the host’s inputs/jobs area, exposed read-only to the agent.

An S3 directory is not a Hawk eval set. Job-readable external logs need native Hawk import/indexing and access permission. Passing a remote source also does not mean every downstream step streams: the audit entry point fetches logs, reads summaries and stages item-specific evidence. This is a remaining scaling bottleneck, visible in the SimpleQA audit startup stalls.

There are likewise three meanings of “logs”: original benchmark attempts, child audit/experiment runs, and the outer investigator’s own Inspect transcript. Keep them separate when measuring coverage, costs or quality.

07

Control lives outside the shell

The model proposes a job configuration. The host-side Policy parses it using Hawk’s config types, checks allowed packages/models/images and bounded settings, then Remote submits through the authenticated Hawk client.

JobLedger records planned reservations and collected costs. Local model spending is persisted too, so workspace recovery carries prior spend forward. Unknown prices remain unknown; they are not treated as free work.

This is not a universal hard spending cap. Inspect’s solver cost limit closes before scoring. Remote reservations include a model-role buffer, but an internally constructed judge can spend outside that solver limit. Use explicit judge configuration, bounded outputs and small smoke tests. Infrastructure and storage costs are a separate scope.

The current shared Hawk identity is not per-investigation identity isolation. Input mounts and submission policy restrict the intended workflow; they do not create separate Hawk users for each auditor. Policy validation is also not a general proof that allowed benchmark Python cannot misuse runner access.

The report is a bundle, not just prose

Readable HTML

Brief: 2–3 sentences introducing the benchmark, then linked finding bullets and coverage. Architecture diagram next. Full audit underneath.

Evidence register

One findings.json with identity, section, claim, status, origin, optional severity, evidence, reproduction and limitations.

Reproducible artifacts

Quarto source, shared styling, source tables, scripts and excerpts accompany the rendered report.

The six detailed sections cover task, grader, harness/environment, aggregation/limits, agent behaviour and construction. Components provide consistent outcome bars, paired comparisons, response matrices and architecture diagrams. Optional IRT analysis uses GIRTH with screening; diverse comparable logs are required, and fitting a model is not evidence that its assumptions hold.

Publication validates structure, unique finding IDs and evidence paths; supported or qualified findings need evidence. It also applies editorial checks and saves a new version outside the writable mount. Referenced input artifacts are included in that version.

Existence is not truth. The validator does not prove that a quotation matches its locator, that a claim follows from it, or that coverage is complete. Independent claim verification and a calibrated report-quality judge remain work to build.

What I would simplify next

First, finish the operational path. Make log inventory, selected evidence retrieval, child-job collection and recovery reliable on one benchmark before increasing the model/eval matrix. Judge authentication belongs in the smoke test.

Then, clarify the package boundary. Keep the investigator as the primary workflow; make the role of the older report entry point explicit. Separate workspace preparation, job dispatch and reporting from the large investigator module without introducing another orchestration framework.

Then, evaluate the output. Blind human review of reports, with evidence correctness and readability scored separately, provides the target for a later judge. The current skill grades are not that evaluation.

What is deliberately not present yet?
  • A fully hosted outer investigator on Hawk.
  • A separate Hawk identity for every audit.
  • A universal remote log abstraction that removes all materialization.
  • Automated verification of every published claim.
  • A calibrated report rubric/judge or optimization loop.
